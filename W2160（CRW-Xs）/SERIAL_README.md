# 串口 W2160 / CRW-Xs：启动、验证与当前边界

本入口针对 2026-10-09 接入的老款 **串口 CRW-Xs**，实测固件 `WATCH crw-x 1.8605 05003`，COM3，**9600 / 8E1**。用户确认这台机只有非接读卡区和一个内部 SAM 槽，没有用户接触式卡槽。本中继只操作非接卡，**不枚举、复位或读写 SAM**。

USB 版尚未到货，未验证；不把新 W2160 USB 手册中的接口、地址或系统命令当成这台老串口机的已知行为。

## 启动

双击项目根目录的 **`start_w2160_serial.bat`**：

1. 枚举 Windows 当前 COM 端口并显示编号。
2. 输入编号或端口名，例如 `1` 或 `COM3`；输入 `Q` 取消。即使只有一个端口，也等待选择。
3. 选择后才独占打开串口，识别握奇固件，寻找非接卡。
4. 卡激活成功后连接本机 VPCD，Windows 的 `Virtual PCD 0` 即可使用。

系统需要 Windows、Python **3.10 或更高版本**及已安装的 BixVReader/VPCD。串口桥接只使用 Python 标准库，不要求 pyserial、32 位 Python、厂商 DLL 或改驱动。原来的德卡入口独立保留。

可选命令行参数：

```powershell
# 人工选择端口（默认）
.\start_w2160_serial.bat

# 自动化时明确指定；不会出现选择提示
.\start_w2160_serial.bat -Port COM3

# 仅列端口，不打开读卡器
.\start_w2160_serial.bat -ListPorts

# 本机实测参数；默认 Parity=auto 会先用 E，再尝试 N，只发固件查询
.\start_w2160_serial.bat -Port COM3 -BaudRate 9600 -Parity E
```

`-VpcdPort` 默认 35963；`-RunSeconds` 默认 0（持续运行，Ctrl+C 退出），可用于短时测试。Python 核心另支持 `--apdu-timeout`，默认给卡片计算 30 秒，并按波特率额外计入线上字节传输耗时；没有自动重发业务 APDU。

端口列表是“系统枚举到的端口”，不预先打开所有串口试探其他硬件。被其他程序占用时明确报错。一个 VPCD 实例一次只能连接一个桥接，不要同时启动德卡和串口桥接争用同一 VPCD 端口。

## 本机协议结论

- **实际串口格式是 8E1**。8N1 在初始测试返回了不可用的数据，不能沿用旧示例里仅打开端口、不调用 SetCommState 的实现。
- 此固件的读卡器系统 NAD 是 **12**，非接 NAD 是 **15**，响应交换高低半字节。系统地址通过只读版本命令验证，SAM 地址不探测。
- 报文 `[NAD][LEN_H][LEN_L][payload][XOR BCC]`，按声明长度收完，检查 NAD/BCC。支持串口拆包，不采用“固定睡眠后只读一次 512 字节”。
- 非接 reset 返回防冲突信息、SAK 和 ATS，前缀随 UID 级联变化。程序验证 ATS 结构并生成 ATR，不固定偏移，不硬编码某张卡的 ATR。本轮卡 ATR 为 `3B8E800180318066B0840C016E01830090001D`。
- 保留复位后 **400ms** 的业务前等待。它是兼容性保护，不宣称所有卡都需要相同启动时间。
- SW `61xx`、`6Cxx` 透明交给上层。桥接不自行修改 CLA、Le、MAC 或重放命令。
- 串口错误、截断、校验错误会使连接不可继续使用，关闭当前 VPCD 会话并重新建立读卡器连接。结果未知的业务写入不自动重试。

## 真实读写验收

2026-10-09 使用用户授权的卡片与管理密钥进行了以下测试，密钥通过临时进程环境交给测试工具，**没有保存到源代码、报告、APDU 日志或启动参数文件**。

### 普通读取与中继

- SDK/DLL 不参与，COM3 直接串口 25 次 SELECT ISD、CPLC、OpenPGP AID、应用数据读取通过。
- 最终版本经 Windows PC/SC 的相同 25 次读取，响应 SHA-256 与直接串口一致。
- 空闲 6 秒后仍可继续读取原应用；RESET、UNPOWER 后重新连接通过。
- 系统固件查询作为每 5 秒空闲健康检查，实测不改变已选应用；它检查的是读卡器本身，不是假装检测到了卡片在位。

### 安全通道和实际写入

用 GlobalPlatformPro 实现认证，验证了 `EXTERNAL AUTHENTICATE -> 9000` 和带 MAC 的后续 GET STATUS。

当前组合用默认 tagged GET STATUS 会收到零数据的 `6310`，工具仍可能退出 0、却漏报应用列表。经参数对照确认，**`--profile old` 的旧式格式可完整枚举原有 18 个条目**。没有修改桥接里的带 MAC 命令来“修好列表”。

独立临时测试包 `F05732313630261009`、实例 `F0573231363026100901` 在确认不存在后才加载：

1. 通过带 MAC 的 INSTALL/LOAD 安装测试包与实例。
2. 用测试应用的 `80 DA` 命令分块写入 1024 字节确定性数据，每次数据块最多 240 字节。
3. 按偏移分段读取，逐字节核对通过。
4. 断开并复位卡片，重新选择测试应用，再次逐字节读回 1024 字节，通过。
5. 单次 240/250/254/255/256 字节读取均通过；更大的扩展请求按下述边界拒绝。
6. 只删除本次测试包及其实例，重新认证、比较注册表。**原有 18 个 AID/类型/生命周期条目恢复一致，测试包与实例均已不存在。**

没有更改用户原有应用内容、PIN、管理密钥或卡片生命周期。测试涉及临时应用 EEPROM 写入、包加载和删除；这不同于声称本轮“没有任何写卡操作”。

## 必须保留的限制

### 短 APDU 与固件保留命令

这版固件不是完整透明的任意 APDU 通道：

- 实测临时 Applet 的 `80 10` 写指令返回 `9000`，但 Applet 没有执行，数据仍为零；更换为 `80 DA` 后写入和读回正常。故该版本上桥接对 **`80 10` 返回 `6D00`**，避免“假写成功”。这会影响同样使用 `80 10` 的协议（例如某些 NFC CTAP 路径），不能承诺任意 Applet / FIDO2 全功能可用。
- 512 字节扩展读曾只返回 256 字节且 `9000`；1024 字节请求也没有得到有效完整响应。**扩展 APDU 和超过 261 字节的命令在发送前返回 `6700`**。短命令最大 255 字节数据，应用需用自己的安全分块；不能擅自把一条签名／带 MAC 命令拆开。
- 256 字节以内响应已通过真实测试；主机收帧代码能接收更大合法长度（并有上限），不代表此固件已支持扩展业务读取。大缓冲区不能弥补读卡器内部截短。
- Type B、存储卡、SAM、其他版本固件未纳入本入口验收；解析不能确认 ISO-DEP ATS 时明确拒绝，不伪造 ATR。

### 空闲取卡、关场、蜂鸣

用户优先要求完善读写，因此这些未验证能力没有用破坏业务状态的办法强行模拟：

- 没找到本固件上已验证无副作用的卡片存在性查询。**目前取卡是在下一次 APDU/复位发现 `6FF0` 后断开，不保证空闲取卡即时通知 Windows。** 读卡器本身的串口失联由健康检查和 I/O 超时检测。德卡脚本原有的主动取卡逻辑没有更改。
- 空数据 RF 探针实测会使后续读卡失败，所以未用于生产代码；周期性 reset/SELECT 也未用作存在性探针，以免破坏安全通道和应用状态。
- 手册 `B0 15 0E 00 01 00` 关场在本固件返回 `6D00`。VPCD OFF 当前使逻辑会话失效，下次 ON/ATR 执行真实 reset；不声称天线持续关闭。
- 检测到卡、取得 ATR 后立即触发提示音，发生在 VPCD 连接之前。资料里的读卡器蜂鸣命令在本机返回 `6FF0`，当前明确提示并用 **电脑短鸣**兜底；尚未实现读卡器本体蜂鸣。提示音失败不会中断读写。
- 没有实际手动移卡／拔串口验收，也未跑完整 AlgTest 或密钥生成/签名压力测试。正常认证、临时安装/写入/读回/复位/删除已验证。

## PIV / OpenPGP / FIDO 兼容性适配（2026-10-09 补充）

针对日常常用应用（PIV、OpenPGP、FIDO），在保持“不改卡片上报能力、不改安全消息、不做片上密钥生成/ECC测试”的前提下进行了专项排查与优化：

### 1. 各应用现状与卡片实测结果

可直接运行诊断工具查询（仅执行公开只读探测，不涉及 PIN、认证、密钥生成、ECC 或任何写入）：
```powershell
python ".\W2160（CRW-Xs）\check_apps.py" --port COM3
```

实机诊断输出总结：
- **OpenPGP**：选择成功（`9000`）。应用数据（00 CA 00 6E，220 字节）、扩展能力（00 CA 7F 66，11 字节）、持卡人数据（00 CA 00 65，30 字节）均正常读取。公钥读取（00 47 81 00）返回 `6A88`（卡上尚未导入/生成对应公钥对象）。
- **PIV**：选择成功（`9000`）。卡片能力容器 CCC（52 字节）、卡片唯一标识符 CHUID（61 字节）均正常读取。身份认证证书（9A）、签名证书（9C）、密钥管理证书（9D）返回 `6A82`（卡上尚未配置对应证书）。
- **FIDO**：卡片对标准 FIDO AID（`A0000006472F0001`）直接返回 `6A82`（卡片上未安装或未激活 FIDO 应用）。另外，由于读卡器 1.8605 固件会拦截并吸收 `80 10`（CTAP2 GetInfo）返回伪造的空 `9000`，中继层对此明确返回 `6D00`，因此在该读卡器固件上 FIDO2/CTAP2 无法正常使用。

### 2. PIV / OpenPGP 扩展只读映射层 (`app_compat.py`)

部分现代客户端（如 GnuPG `scdaemon`、PIV 工具）会默认以**扩展 APDU / 扩展 Le**（Le > 256）请求证书或公钥数据。老串口固件只支持短 APDU，直接下发扩展格式会导致返回 `6700` 或截断。

为此在中继层加入了**受限扩展只读映射**：
- **严格范围限制**：仅针对显式选中 PIV 后的 `GET DATA`（`00 CB 3F FF`），以及选中 OpenPGP 后的 `GET DATA`（`00 CA`）和公钥读取（`00 47 81 00`）。
- **线上下发短 APDU**：将扩展请求转换为短 APDU 发送给卡片，并通过 ISO 7816-4 标准的 `61xx` + `GET RESPONSE`（`00 C0 ...`）多轮拼装完整数据。
- **安全隔离原则**：PIN 校验、写入命令（PUT DATA / IMPORT）、片上密钥生成、安全消息传递（Secure Messaging）**一律不作转换**，不擅自拆包或修改参数。
- **状态隔离**：卡片复位、断电、关闭逻辑通道或 SELECT 任何其他应用时，立即清除当前应用状态，避免跨应用误映射。
- **BER-TLV 校验**：对拼接后的数据验证 BER-TLV 完整性，防止固件静默截断造成假数据。

### 3. GnuPG (`gpg --card-status`) 实机验证与配置注意

在 COM3 真实中继下运行 `gpg --card-status` 验证，已成功读取 OpenPGP 智能卡的完整状态（Reader, AID, version, vendor, url, sigcount 等）。

> [!IMPORTANT]
> **Windows 下 GnuPG 独占冲突注意**：
> Windows 环境下的 GnuPG `scdaemon` 默认以独占模式（`SCARD_SHARE_EXCLUSIVE`）打开智能卡。由于 VPCD 或 Windows Smart Card 服务可能持有卡片句柄，`scdaemon` 容易报错 `pcsc_connect failed: sharing violation (0x8010000b)`。
> **解决方法**：在用户的 `%APPDATA%\gnupg\scdaemon.conf` 中添加：
> ```text
> disable-ccid
> pcsc-shared
> ```
> 即可使 `gpg --card-status` 和其他 OpenPGP 操作与 VPCD 中继无缝配合。
